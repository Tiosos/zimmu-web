# Cabinet opening layouts

- Implements fifteen cabinet-design improvements: 2–8-way splitting, panel/rail/front-only construction, resolved opening dimensions, fixed sizing from actual dimensions, percentage sizing, sibling equalizing/reversing/moving both ways, five ready-made shelving/door/drawer layouts, and validated preview/apply with separate undo history.
- Uses the existing section tree, material overrides, carcase validator, panel generator, elevation and drawer regeneration. No new file format or geometry engine. Horizontal children remain bottom-to-top; vertical children remain left-to-right.
- Layout replacement preserves the selected section ID/size and unrelated branches, creates fresh child IDs and drops independent frame layouts only for replaced sections. The preview explicitly describes the replaced contents. Unsupported face-frame geometry and invalid/missing material dimensions block application.
- Preview validity depends on params/selection/materials and the role-override signature, not generated mesh identity, so asynchronous meshing cannot close a valid preview. Updaters reject a changed base params object or a different cabinet before writing.
- `onUpdateComponent` gains the same optional history-label behavior already used by part edits: labeled structural commands do not coalesce with dimension typing or another layout. Missing and no-op component updates do not create history entries. Scene-hook tests exercise real drawer regeneration and separate undo/redo snapshots.
- Keyed fixed/percent dimension editors preserve their target through unmount debounce flushing; error messages are scoped to the attempted params/selection so an error from another opening does not linger.
- Rejected numeric edits remount only the affected dimension editor to display the retained model value. Without this, a rejected 150% attempt left 150 visible while the model still held 30%. A regression also checks immediate opening switches: pending fixed-size input flushes to its original section, not the new selection.
- Regression verification: targeted tests passed before thirty deliberate mutations covering split guards, reordering/equalizing, identities, frame cleanup, template dimensions, geometry checks, fixed/percent sizing, rejected edits, preview expiry, stale apply guards, debounce targets and history boundaries. The history test initially depended on another describe’s worker setup when run alone; gave it its own mock mesh result, confirmed the isolated test passed, and reran the three history mutations to get assertion failures. All mutated source files were restored from scratch backups and compared byte-for-byte afterward.
- Final review found that all-fixed child sizes could exceed their parent while retaining positive dimensions. Reproduced with failing root/nested tests, then tightened the shared carcase validator to check containment in both axes (with numeric tolerance). Equalize remains available to repair an over-constrained group after narrowing the cabinet. Both new guards were separately mutated and restored; the restored focused tests passed.
- A second regression reproduced three positive front cells with drawer boxes too short to generate. Layout previews now use the real drawer generator and require every new drawer’s five box roles; unsupported runner depths also block apply. This is scoped to the replaced opening and default new drawer configuration, preserving unrelated drawer design. Generic cabinet validation still uses existing carcase geometry rules.

- Final validation: 191 unit-test files passed (3,403 tests passed, 10 skipped), both new Chromium workflows passed, and typecheck, lint and production build passed. The execution environment disconnected before reporting the full-suite result; the recovered log confirmed completion. The final drawer-box fit, preview geometry and stale-selection guards were also deliberately mutated, produced the expected assertion failures, and were restored before this run.
