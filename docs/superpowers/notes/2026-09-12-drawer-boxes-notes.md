# Drawer boxes — implementation notes

**Spec:** `docs/superpowers/specs/2026-09-12-drawer-boxes-design.md`
**Plan:** not yet written

Living record of decisions that do not belong in the spec — why an approach was rejected, what was
discovered during implementation, and anything that would surprise a future reader.

## 2026-09-12 — how this stage was chosen

The driven hardware BOM merged on 2026-09-11 as PR #45. Nothing carried a *Next* badge afterwards,
so the choice was made from evidence rather than from a roadmap entry.

The roadmap in `project-structure.html` has exactly two rows not marked Done: the File System Access
API fallback (*Planned*) and the Rust/Tauri shell (*Phase 1*). Neither is blocked on anything, and
the first advances the shell rather than the cabinet model.

The stronger signal was the cabinet-assembly restructure spec's excluded-scope list, which named
four things. Three are now resolved or blocked elsewhere: hardware in the BOM shipped, face frames
need a face frame first, vendor catalogues are a lookup over constants that now exist. Drawer boxes
were the one left — and unlike the others, two shipped figures are recorded **in two separate specs**
as waiting on them. `carcaseRoles.ts` even carries a comment at the line where the slide height is
derived saying the figure is expected to move.

So this stage was picked because the code itself says it is pending, not because it seemed like a
good idea.

## 2026-09-12 — the architectural contradiction, found before designing anything

The 2026-08-18 cabinet-assembly design says, in as many words: "Fronts (doors, drawer boxes) are
**child components with their own generators**, not carcase parameters."

That is not what shipped. Fronts are carcase roles emitted by `carcaseBoxes` as
`front-{sectionId}-{leaf}`, and `Component` is still `GroupComponent | CarcaseComponent` — there is
no front component kind. Verified by reading `types.ts`, not inferred.

So the written intent and the built precedent disagree, and the drawer-box decision could not be
taken without picking one. It was put to the user that way. The recommendation was to follow the
shipped precedent (carcase roles) on cost grounds; **the user chose the child component**, which
realises the original intent rather than contradicting it a second time.

Recorded because the cheaper option will be proposed again by anyone who counts the lines, and the
reason it was declined is not a cost argument.

## 2026-09-12 — the cycle, which is the real content of this design

Halfway through proposing pipeline options it became clear the obvious shape is circular. Slide
screws are bored into carcase uprights at a height that comes from the box; the box is generated by
the drawer; the drawer needs the carcase's front cells. Carcase → drawer → carcase.

That would break the generator's stated one-direction invariant in exactly the way CLAUDE.md warns
about for thickness overrides: the pass stops being a function and becomes a fixed-point iteration.

The resolution is the pattern already used three times in this codebase — `pinRow`, `clearDepth`,
`frontCells` — state the rule once and let two callers read it. `drawerBoxMetrics` is a pure
function of the front rect, the drawer params and the materials. Neither generator reads the other's
output.

Worth noting *when* this was found: while enumerating pipeline options, not while implementing. Had
it surfaced during implementation, the likely outcome is a two-pass convergence nobody notices until
a cabinet needs a second edit to settle.

## 2026-09-12 — why drawers run first

Given the shared-metrics function, the drawer stage could in principle run anywhere. It runs first
because the carcase's machining reads drawer *parameters* while the drawer reads nothing the carcase
*emits* — its inputs are the section tree, the drawer params and the materials, all available before
the carcase pass.

Run the other way round, the first pass after an opening becomes a drawer front bores no slide
screws and the second does. That is convergence over two passes, not idempotence in one, and it
would present as a rendering glitch rather than a pipeline bug.

## 2026-09-12 — a defect this work would create, found at design time

`carcaseHardware` resolves a part's owner with a **direct**-parent check:

```ts
const owner = part.parentId !== null && carcases.has(part.parentId) ? part.parentId : null
```

A drawer board's parent is the drawer component, not the carcase, so every screw holding a box
together would tally under `Ungrouped`. Not dropped — `Ungrouped` is emitted — but attributed to no
cabinet, which on a multi-cabinet job makes the figure useless.

The cutting list does *not* have this problem: `groupParts` already walks ancestors via
`ancestorsOf`. So the fix is to make the hardware pass use the same helper, which makes the two
agree by construction instead of by coincidence.

Both halves of that were checked by reading the code. The instinct was that both would be broken;
measuring showed one already worked. That is the third time this session that a claim reasoned about
was wrong and a claim measured was right.

## 2026-09-12 — two decisions taken against a recommendation

Both are the user's call and both are recorded in the spec, but the reasoning behind the caveats is
worth keeping here so it is not re-litigated from scratch.

**The runner offset as a parameter.** The driven hardware design declined to add vendor parameters,
reasoning that a hardware item will eventually carry its own geometry and a parameter added now
would be orphaned then. That argument still holds. It is outweighed here by decision 2: once a
drawer is a component with its own params, a per-drawer runner offset has an obvious home, and the
"orphaned parameter" risk is a migration rather than a design flaw. If the vendor model lands, this
parameter and the box height are the two to migrate away.

**Box height as a parameter rather than derived.** The derived-only rule cannot express a shallow
box behind a tall front, which is ordinary where plumbing or a rail is in the way. Accepted without
much argument; noted only so nobody "simplifies" it back to derived-only later.

## Open questions for the plan

- **The two hardware figures.** The runner allowance per side (13 mm) and the runner height above
  the box bottom ship at stated values pending a woodworker's confirmation. Side-mount and
  undermount systems differ materially and the spec does not model that difference. These are the
  same risk class as the hinge-count table: no test in this repo can falsify either.
- **Which fixtures re-baseline.** Re-basing the slide height moves shipped machining positions.
  The plan must **measure** which fixtures and which projections change rather than asserting none
  do. The sheet-yield spec made exactly that mistake, claiming a change re-baselined nothing when
  it re-baselined real rows.
- **Stale selection when a drawer disappears.** `regenerateDrawers` is the first pass to remove
  components. A selected drawer whose opening became a door leaves a selection naming nothing. The
  section-pick rules already learned this lesson once; the plan should say which of those rules
  applies rather than inventing a fourth.
